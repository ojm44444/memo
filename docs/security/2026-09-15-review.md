# Security gate, 15 September 2026

Asked for after Samply went offline with a security incident. Four items: share link controls, a
second pair of eyes on storage and row level security, sign out everywhere, and a backup actually
restored. This records what was found and what was done, so it can be checked rather than trusted.

## Exposure

None. `auth.users` holds one account (the owner's). There are no `board_members` rows. A scan for
rows each hole below could have produced (invites made by a non-owner, shares whose song is on
another board, takes pointing into another user's folder, comments by outsiders) returned zero.

## 1. Independent review of storage and row level security

A separate reviewer, who had not written any of this, read the live policies, grants and definer
functions. Every finding was then re-checked on production before anything was changed. Fixed in
migration `034_close_share_and_invite_holes.sql`.

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | Critical | `board_invites` insert only checked `created_by = you`. Anyone signed in could write an invite for any board and accept it, becoming a member who can read every song, lyric, note and take. | Must own the board to create, read or change an invite. |
| 2 | High | `song_shares` insert/update only checked `created_by`. A share of someone else's song could be made, which its owner could not see or revoke. | No direct writes at all; shares only through `create_song_share`, which checks ownership. The listen RPC refuses a pinned take from another song. |
| 3 | High | A take's `storage_path` was free text: point it at another user's file, then share it, or trash it and let the retention sweep delete their file. | A take's path must be in the writer's own folder. Both retention functions only return paths in the owner's folder. |
| 4 | High (no rows yet) | Playlist links were readable by anyone, logged out included. Every playlist token on the service could be listed with the public key. | Owner only. Playlist tokens are now 128-bit, like song links (were 48). |
| 5 | Medium | Board comments could be posted into any board, as any user. | Post as yourself, on a board you can access, about a song on it. Owners can remove any comment on their board. |
| 6 | Medium | Bandmate invites were reusable by anyone for 30 days. | Used up by the first person to accept. |
| 7 | Functional | **Share links did not play for anyone without an account.** The storage rule for shared audio queried tables the anonymous listener cannot see, so it never matched. Verified as the anon role: 0 rows. Owners and testers were always signed in, which is why nobody could reproduce the "never plays" report. | The check runs in a definer function that releases exactly the take the listen page serves, only while the link is live. Verified as anon: the served take loads, other takes of the song do not, an unshared song does not, a revoked link does not. |
| 8 | Low | No length cap or rate limit on listener comments; the feedback email ignored link expiry; API roles held TRUNCATE. | 2,000 character cap, 60 per link per hour; expiry checked; TRUNCATE, TRIGGER, REFERENCES revoked. |

**Why the live policies were weak.** Production's policies on `board_invites`, `song_shares` and
`song_comments` were not the ones the migrations created. They had been rewritten to the
`(select auth.uid())` form the performance advisor suggests, keeping only that half of each check
and dropping the ownership half. No migration records it. Rule: every policy change is a migration
file.

**Still open from the review:** no limit on share-password guessing (bcrypt, default cost).
Raising inside the function rolls back any attempt counter, so it needs the listen RPC to return a
wrong-password result instead of raising, which changes the share page. Low while there are no
customers; do before launch.

**Honest limit of this review.** It was a second model, not a second person. It found things the
first pass missed, which is the point, but a human review before launch is still worth having.

## 2. Share link controls (migration 033)

- A lifetime is chosen when a link is made: 1, 7, 30 or 90 days, or never. 90 is the default.
- Playlist links can be revoked (there was no way to before) and take the same lifetimes.
- Settings, Share links: how many song links, playlist links and unused invites are open, and one
  button that revokes all of them. Revoked links stop playing immediately, because the storage rule
  checks the link, not a cache.
- Revoking a link no longer hides the comments left on it.

## 3. Sign out everywhere

- Settings, Account: "Sign out everywhere" revokes every session for the account.
- Other devices lose cloud access when their current access token expires. Measured on production:
  sessions refresh every 59 minutes, so within the hour.
- It does not wipe songs already saved in another browser. Deliberate: the app keeps a device's
  board when a sign-in is refused, because a refusal can also be a captive portal or a rate limit,
  and wiping on those destroyed unsynced takes before. The Settings text says so.
- Found on the way: the plain "Sign out" button was ALREADY signing out every device, because the
  Supabase library's default scope is global. It now signs out this device only.

## 4. A restore actually performed

- `src/lib/export/backupRoundTrip.test.ts`: builds the zip from a board, wipes the device, restores,
  and compares every record and the SHA-256 of every audio file. Runs in CI.
- The same round trip run in Chrome on the demo board, twice (over the board, and onto an empty
  "new device"): 11 of 11 songs, 18 of 18 takes, 18 of 18 audio files byte-identical.
- Two bugs found by doing it:
  1. The restore rebuilt each take from nine named fields and dropped the rest: tags, trim points,
     and take/mix/master were lost on every restore. The test fails on the old code.
  2. A restore in a real browser left fifteen "My Project"s. While the project table was briefly
     empty, about ten live queries each created a default project at once. Creation is now
     single-flight and transactional, and the restore swaps projects in the same transaction as the
     wipe. This is also a road to the duplicate projects seen on fresh browsers.
- Also fixed: backup files are named `songdrafts-backup-DATE.zip` (were `memo-`), and each audio
  file keeps an extension that opens it (AIFF, FLAC, CAF were all named `.m4a`).

**Not yet done:** a restore of the owner's real library. It needs a backup exported from the
machine that holds the audio.

**Server-side backups.** Supabase's daily backups cover the database. They do not include the
files in Storage, so the audio bucket has no server-side copy. A decision is needed on whether to
add one (for example a scheduled copy to a second provider).
